# Working with someone else's API should cost less than working around it

AAT models an API as a graph once. Tests, matrices, an MCP server, and shareable run records all read the same file. This is the story of why, first published on [vec.com](https://vec.com/).

<!-- more -->

AAT started as a pile of Postman collections.

They worked, at first. Then the team grew. Everyone had their own copy with their own tweaks, and none of them were reliable. Nothing was in source control, so there was no diff, no review, and no way to tell whose version was right. Every new test case meant editing a collection in place, so the case it replaced was gone. The chaining lived in pre-request scripts, which put the interesting part of a flow, what depends on what, inside JavaScript instead of in front of you. And none of it was legible to an AI coding tool: the export was one file too large to read, in a shape nothing else consumes.

The underlying problem is that real integrations are not one call. Buying something means browse, cart, checkout, pay, ship, and maybe return and refund: 8 to 20 calls, each needing IDs from the calls before it, leaving state behind that someone has to clean up. A collection is a folder of single requests. Everything that makes those requests a *flow* has to live somewhere else, and that somewhere was scripts.

Postman is good at what it is for: exploring an API by hand, one request at a time. It is a poor place to *keep* the knowledge of how an API works. That knowledge ends up in a format only Postman reads, in a workspace rather than your repository, and it scales by copying.

## Twelve calls, three files

So the knowledge moved into the repository, and it split into three things that had been tangled together.

**API knowledge** is a graph of operations and request templates, written once. A node says what an operation takes, what it returns, where each input's value comes from, what must run before it, and what undoes it:

```yaml
checkoutCart:
  adapter: checkoutCart
  inputs:
    - name: cartId
      default: {from: createCart.cartId}    # wired from an earlier step
    - name: shippingTier
      type: enum[standard, express, overnight]
      default: standard
  outputs:
    - name: orderId
  cleanup: deleteOrder                      # undone after the run
  requires: [cartPopulated]
  satisfies: [orderCreated]
```

**Test intent** is a plan that lists steps, not wiring. This is a whole test:

```yaml
kind: recipe
selection:
  workflow: Checkout
  choices: {customer: Registered, payment: PayPal}
  addons: [Apply Coupon, Return After Delivery]
```

**Variation** is layers and environments that turn one plan into a matrix. A layer is a named set of input values; each `--layer-group` adds a dimension. The demo shop's batch runs 7 plans across 9 permutations, skips the 36 runs that would repeat another run's requests, and passes the other 27, from one command, with nothing copied.

![aat run batch with two layer groups: the dedup list, four progress bars, and Batch: 27/63 PASSED, 36 SKIPPED](https://raw.githubusercontent.com/gburgyan/aat/main/docs/user/assets/demo-batch.gif)

Small files, reviewed like code, that a person can follow without opening a debugger. The point is not that the files are tidy. It is that they run.

## The hard calls

AAT was built for a private airline booking API: 74 operations, 63 workflows, 53 recipes, 6 environments. Some of its calls were very hard to get working even with the full documentation and mostly working collections in hand, which is what any customer integrating by hand goes through.

What changed was the loop. A coding agent with `aat` in front of it could edit one small file, run the plan against the real sandbox, read the exact request and response, check the docs, and try again. Calls that would have taken hours or days by hand came together in ten to fifteen minutes each. [One call's story here, in renamed vocabulary: what the docs said, what the API actually wanted, how the archive showed the difference.]

An agent is only as good as its feedback. Set up the feedback first (a validator, a real run, a precise error), then let it iterate; without that, it guesses. [Optional aside: the same approach on a firmware project.]

## Why the files fit in an agent's head

The airline API ships a 40,000-line OpenAPI spec, and the team's collections for it were 21 and 23 MB. The AAT project that replaced them is a 3,708-line graph for 74 operations, with a median request template of 23 lines. An assistant, or a reviewer, loads the one operation the task needs and edits one file.

And the loop closes before any request is sent. Project files are decoded strictly: an unknown key is an error that names the line and the nearest valid key. `aat validate --strict` catches broken wiring, a plan that names an output nothing produces, and a template that disagrees with the spec. During the run, `--oas-validate` checks every request and response against the OpenAPI document, and the archive keeps the actual exchange.

## What else could read it

Once the API was described well enough for the engine to run it, the description turned out to be worth more than the tests it was written for. The question stopped being *what else should this run?* and became *what else can read this?*

The MCP server was the first answer. `aat mcp serve` hands an AI coding tool the same graph the engine runs: each operation's exact request, the order calls go in, what each needs from the calls before it, the composed flows, and sample responses from real runs. It is a form a machine can act on rather than prose it has to interpret. On the airline API, that was enough for a working search-and-booking client from a single prompt, in Java, C#, Go, Python, Perl, and Lisp. The same test on the demo shop is reproducible; the docs have the prompt and the results of a Python run and a Go run.

The run archives were the second. Every request, response, resolved value, retry, and assertion is recorded, and a run exports as a single file that someone else opens in the same viewer. It is how you show that something works, or that it doesn't, with the actual exchange rather than a screenshot of one pane.

![The shop's checkout step in the web UI: the request, Copy as cURL, headers with Authorization redacted, and the JSON body](https://raw.githubusercontent.com/gburgyan/aat/main/docs/user/assets/ui-step-request-curl.png)

Neither was a roadmap. Both fell out of having the graph, and that is what the *toolkit* in the name means. *Adaptive* is the other half: the many ways one graph runs, across layers, environments, per-operation overrides, checkpoints, batch matrices, and the MCP server, without a copy of anything.

## Proof, in public

Three complete projects run AAT against real, public APIs in their test modes, and every number in their READMEs is something a run recorded:

| Project | Scale | What it shows |
|---|---|---|
| [aat-duffel](https://github.com/gburgyan/aat-duffel) | 66 operations, 47 plans, 14 layers; 47/47 in ~3½ min | Flight search and booking against an API with no official OpenAPI spec |
| [aat-stripe](https://github.com/gburgyan/aat-stripe) | 82 operations, 53 plans, 14 layers; 53/53 in ~5 min | Card and bank payments, with every exchange checked against Stripe's 205,000-line spec |
| [aat-shippo](https://github.com/gburgyan/aat-shippo) | 46 of 70 operations, 28 plans, 9 layers; 28/28 in ~2½ min | Rating, buying, refunding, and tracking shipments; layers as the headline; real labels in the web UI |

Each is a project you clone, export a free test-mode key into, and run. Each is also a worked integration: the graph and its domain file are a reference whose every claim has a run behind it, and `.mcp.json` hands the whole thing to a coding assistant.

Before those were built, a different question was asked: can an agent build such a project from the public docs alone, with no help? It can. In clean rooms, from one prompt each, coding agents built a Duffel project (twice) and a Stripe project (three times, about thirty minutes each). Every attempt validated clean and passed every plan it wrote; the Duffel runs handled 13 of 14 asked-for flows unaided, the Stripe runs 13 of 13. The first try is the headline, and every attempt is reported. The rooms are not published; the projects above were then built openly, with the author, as the versions worth shipping.

## When the API is wrong

Running against a spec finds things reading it does not. Stripe's own OpenAPI document does not describe one of the responses its API sends. Shippo's marks nothing as nullable, and the API sends `null` constantly. In both projects the finding is pinned by a plan, reported rather than fatal, and counted on every run. That is the kind of thing strict validation exists to find, and the archive is what you attach when you report it.

## Honest scope

LLMs are optional and authoring-time only: `aat prompt` can draft a plan, and the MCP server teaches AI tools your API. Execution never calls an LLM. The loop needs an API it can call, so a sandbox or a test mode. There is no Postman importer; the on-ramps are `aat generate --oas` from a spec, or an assistant reading a collection through a reader and closing the loop with a validator and a run. It is pre-1.0 with one maintainer, and the formats may still change.

## Try it

```bash
brew install gburgyan/tap/aat        # or a release archive, Docker, go install
aat-sandbox init shop && cd shop     # the offline demo project
aat-sandbox serve &
aat run plan full-lifecycle          # one order through every state, verified and cleaned up
aat web view latest
```

The docs are at [gburgyan.github.io/aat](https://gburgyan.github.io/aat/), the code at [github.com/gburgyan/aat](https://github.com/gburgyan/aat), and the three projects are linked above.
